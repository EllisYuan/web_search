Web Search MCP 选型

先分清谁负责“深度”，再选择搜索与读取组件。目标是为 agent 提供可验证的联网能力，而不只是返回更多链接。

适用对象：正在确定首版边界的开发者。依据：公开 specs、official docs 与 source code；不含收费 API 实测。

能力边界先于技术栈

用户目标是一个通用的深度 Web Search MCP，让不同 agent 能够联网搜索。本次请求是调研，不是授权实现；“通用”暂按不绑定某个 model provider 处理，“深度”的具体产品含义仍需用户确认。

本轮没有代替用户完成选型。

文中的推荐是用于讨论的候选路线。预算、部署模式、首批 MCP clients 和输出形态均未获确认；Wayfinder 的 HITL ticket 保持开放。

推荐候选：host-driven research + 受控检索服务。

MCP 提供 search、read、evidence 与预算执行；外部 agent 做问题拆解、query rewrite、多轮追查、冲突判断和最终 synthesis。首版不要求 MCP server 另持一把 LLM key。

职责实际解决的问题不等于
Search发现候选 URL、排序、摘要、日期与地区过滤已读到完整正文
Fetch / Extract获取指定网页并抽取正文、结构和 metadata全网检索或可信答案
Crawl / Browser受限地遍历站点，或执行 JS / 必要页面交互绕过登录、paywall 或访问控制
Research持续发现信息缺口，查找和核对证据，决定何时停止单次 search 返回更多 results

MCP 是工具与上下文的连接协议，不是 search index，也不自动附送研究智能。对“比较两种技术在特定约束下的取舍”这样的题目，深度来自多轮检索和交叉验证，而不只是一个名为 deep_search 的参数。

架构推荐是工程判断；协议角色与边界依据 MCP specification。应用自定义的 search/read 工具名称不是 MCP 标准工具。

Search providers：按职责选择，不按品牌堆叠

首版只需要一个 primary provider。可替换 adapter 的价值在于保留选择权，不是起步就接入所有服务。以下是依据官方文档的产品定位，不是召回质量排名。

候选值得考虑的场景主要取舍
Brave需要较纯粹的通用 Web search 与语言、地区、freshness 控制Search 结果不等于完整正文；缓存和数据使用受套餐条款约束
Tavily希望一套 API 覆盖 search / extract / map / crawl不同操作按 credits 计量；hosted research 必须另设预算
Exa需要 semantic search、内容检索、domain/date 条件中文质量须实测；Search 与独立 Contents 的计价边界需按实际调用区分
Parallel面向研究目标的 search + extract，返回适合 agent 的 excerpts搜索模式与 hosted task 不是同一产品；官方 free quota 页面有不同口径
SerpAPI需要 Google / Baidu 等特定 engine 的 SERP、地区和语言参数engine 语义各异；分页额外消耗 search，不提供统一的正文质量保证
SearXNG愿意维护自托管 metasearch，重视实例日志与网络出口控制上游可用性、限流和实例维护由自己负责；不是独立 index
SearXNG 不等于 query 不外发。

自托管让你控制中间层，但 query 仍会发往配置的上游 search engines。若约束是“query 不能离开自有网络”，这些公开 Web search 路线都不能直接满足，需要可获准的 query 改写/外发策略或本地数据集。

Build-vs-buy 的实际分界

Brave、Tavily、Exa、Parallel、SerpAPI 已有官方维护的 MCP repo 或 endpoint。若目的只是“让 agent 联网”，直接使用它们是合理基线。自己写 MCP 的理由应是统一 provider、evidence 格式、权限、budget、cache 或检索策略，而不是重复包装已有 HTTP endpoint。

“官方 MCP repo 开源”不代表后端 API 免费，也不授予网页内容的长期保存或再分发权。SearXNG 主项目的 HTTP API 与第三方 MCP adapter 也应分别审查。

成本口径与旧教程陷阱

调研时 Brave 公布 Search $5 / 1,000 requests；Tavily PAYG 为 $0.008 / credit，Basic Search 为 1 credit，Advanced 为 2 credits。10,000 次调用的示例分别是 Brave $50、Tavily Basic $80 或 Advanced $160，均忽略 free quota、正文读取、模型和基础设施费用；这不是同等效果的价格排名。

Parallel 的不同页面出现 5,000 与 80,000 free requests 的口径，未将其作为预算承诺。Exa 普通 API retention、Tavily zero-retention 表述与一般 Privacy Policy 的关系，也需要在采购前核对合同适用范围。

Google Custom Search JSON API 已停止新客户接入，现有客户迁移截止为 2027-01-01；Bing Search APIs 已于 2025-08-11 退役。不要照旧教程把它们作为新项目默认依赖。

读取网页：便宜路径优先，升级必须有边界

找到了正确 URL，不代表已经取得可引用内容。建议按明确失败条件升级 extraction，而不是每个页面都启动 browser。

  1. 默认静态层：Python 用 HTTPX + Trafilatura；TypeScript 用 fetch + Readability，后者需 DOM 解析环境。保存允许保存的原始表示，再抽取正文；声明截断与失败。
  2. 按需 browser 层：只有 JS shell、延迟 hydration、必要展开等情况才使用 Playwright；需要现成 crawl 和 Markdown 能力可评估 Crawl4AI。设置 wall time、页面数、bytes、子请求和并发限制。
  3. 可选 hosted 层：Firecrawl / Jina Reader 可减少部分抓取运维，但 URL、内容、日志和缓存可能进入第三方服务。不得把 hosted fallback 当成自动允许的数据外发路径。

PDF 应按 content type 走独立 parser；text PDF 与扫描 PDF/OCR 是两类需求。Crawl4AI 官方 PDF 文档明确 OCR 不是内置能力；Playwright 的打印 PDF 功能也不是 PDF 读取能力。

Evidence 是可复核记录，不是 URL 装饰

建议至少返回 source_id、url、final_url、title、retrieved_at、content_hash、content、locator、truncated 和 warnings。区分抓取时间与 published_at；后者未知时不猜。

原始表示与 extracted text 分别计算 hash，并记录 extractor 版本。HTML 引用指向对应 snapshot 的 section/offset，PDF 指向 page/block。hash 可以发现内容变化，不能证明来源真实性；source 的保存还必须受版权、provider terms 与 retention policy 约束。

安全、license 与数据流细节

SSRF：对 URL、DNS A/AAAA 和每个 redirect 做检查，限制 loopback、私网、link-local 与 cloud metadata；browser 的子资源也属于攻击面。Playwright route 不是网络隔离边界，应配 egress policy，并注意 service worker 可能绕过 route。

Prompt injection：网页正文、HTML comments、alt text、OCR 都是不可信数据，不能变成 system/developer instruction。HTML sanitization 处理 XSS，但不等于解决 prompt injection。引用 ID 由系统生成，引用内容仍需验证。

访问与许可：robots.txt 不是授权凭证；遇到未授权登录、paywall、CAPTCHA 或拒绝访问，返回明确状态而非绕过。Firecrawl 主 repo 为 AGPL-3.0；Crawl4AI 为 Apache-2.0。Jina Reader 服务、ReaderLM 模型和商业 on-prem 不是同一许可对象。开源 self-host 不保证与 hosted 同等能力。

Firecrawl 配置提醒：本次 scrape reference 的 skipTlsVerification 默认 true、storeInCache 默认 true、zeroDataRetention 默认 false。生产配置应显式要求 TLS verification，并审核缓存与数据保留；这些是文档事实，未进行端点实测。

协议已变化，旧示例不再是统一基线

2026-07-28 specification 引入 stateless、自包含 request 与 per-request capabilities；新版 Streamable HTTP 以 POST 为主，可返回 request-scoped SSE，不再依赖旧 GET stream、protocol session 或 Last-Event-ID resumability。这里的 SSE response 与 deprecated 的 legacy HTTP+SSE transport 不是一回事。

本地优先 stdio，日志只能写 stderr；remote 用 Streamable HTTP，并处理 auth、Origin 与 token audience。新版 Sampling 已 deprecated，不适合作为新研究服务的必需依赖。

Tasks 是 opt-in extension，SDK 支持和 host 支持必须分别核对。基础路径应能用同步 bounded call 返回结果或明确 partial；不能只给 host 不认识的 task handle。大内容可用 resources，但必须为不支持该读取路径的 client 保留 read/section/pagination 方案。

版本由官方 release 交叉核验；并未安装 SDK 或做 host conformance。来源：Python release · FastMCP release · TS v1 release · TS v2 release · Transport · Deprecated registry

三条可行路线

直接使用官方 MCP · 最少自建代码

适合只需要给已有 agent 增加联网能力。选择 Brave / Tavily / Exa / Parallel 等现成 MCP，让 host 做多轮 research。优点是能先验证使用价值；代价是工具形态、数据流与政策更依赖 provider。

自建薄 MCP + 可替换 provider · 本项目的推荐候选

用 official Python SDK 或 standalone FastMCP，接一个 search provider，静态读取优先，必要时 Playwright/Crawl4AI。自己拥有统一 schema、evidence、budget 和错误处理，但不重复建设 search index 或再嵌一个 LLM agent。

SearXNG + 自托管读取 · 更多运维控制

适合愿意管理 search 实例和 browser 资源的场景。软件没有 hosted Search request fee，但服务器、上游服务、网络出口、限流和维护不是零成本。它也不解决 query 必须留在本地的硬约束。

首版能力建议

  • search(query, ...)：发现来源；保留 provider/engine 语义，不把不支持的 filter 静默当成已执行。
  • read(url, ...)：读取受限内容、定位 section、返回 evidence metadata；明确 partial、truncation 和访问失败。
  • 运行边界：per-call timeout、absolute deadline、有限 retry、max pages/bytes/concurrency、明确 quota。
  • 本地小规模可采用受条款约束的文件/SQLite cache；无需先部署 Redis、Postgres、vector DB 或多 agent graph。

只有“一次调用必须返回完整研究报告”成为明确需求，才考虑 server-driven planner、model adapter、持久 job 与 synthesis。LangGraph 等框架是那时的选项，不是联网搜索的前置依赖。

验证质量与成本，不做未经测试的排名

本轮完成的是 documentation research，不含 provider benchmark。中文质量、实际 freshness、抓取成功率、p95 latency 和每个完成任务的总成本都仍是未知量。

C_task = C_search + C_extract + C_browser + C_model + C_infra

这个式子只统计实际发生且未被其他套餐包含的项目，不能对 bundled Search/Contents 重复计费。host-driven 不等于没有 model cost，只是该费用留在 host。free quota、cache hit 与失败是否计费也应分别记录。

硬预算必须能在发起请求前预留额度并在 usage 返回后对账；如果 provider 没有可用的上界，就只能称 estimated budget。取消通常是 cooperative，已发起调用可能已经产生费用，断开连接不等于退款。

验收门槛需由实际使用场景决定；此处没有捏造成功率、工期或美元预算。

研究可以自主完成，偏好不能代答

需要确认的是产品职责，而不是要求用户先懂每个库。下面这些边界将改变后续方案：

  • agent 自己规划搜索并写答案，还是调用一次 MCP 就拿到完整研究报告？
  • 优先服务本地个人使用，还是面向多人提供 remote MCP？首批需要兼容哪些 clients？
  • 允许使用哪些付费服务、怎样约束单次任务预算与等待时间、哪些 query 不允许外发？
  • 以中文网页、英文技术文档、新闻时效还是跨来源比较为首批验收场景？

确认深度搜索的产品边界与首版取舍是需要用户实际参与的 HITL ticket。这里没有将建议写成用户答案。
